# 发票详情页跳转付款页面链路分析报告

## 1. 概述

本报告聚焦一个看似简单但实际暗藏陷阱的链路：**从发票详情页点击「记录付款」跳转到付款创建页面**。具体分析以下三个问题：

1. **路由中的 `:id` 指向哪个对象？** — 同一个 `route.params.id` 在不同路由下含义截然不同
2. **客户切换后这个值为何会出现在重新取号请求中？** — `route.params.id` 的语义混淆问题
3. **后端如何解析 `model_id`？** — `setModelObject()` 在不同场景下的行为差异

## 5. 客户切换后 `model_id` 出现在取号请求中的原因

### 5.1 selectNewCustomer 的代码

**代码位置** [Create.vue:L519-L530](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/resources/scripts/admin/views/payments/Create.vue#L519-L530)

```javascript
function selectNewCustomer(id) {
  let params = {
    userId: id,
  }
  if (route.params.id) params.model_id = route.params.id

  paymentStore.currentPayment.invoice_id = null
  selectedInvoice.value = null
  paymentStore.currentPayment.amount = 0
  invoiceList.value = []
  paymentStore.getNextNumber(params, true)
}
```

### 5.2 `model_id` 传入的意图

`model_id` 的设计意图是：**在编辑已有单据时，告诉后端当前单据的 ID，以便保留已有的 `sequence_number`**。

后端收到 `model_id` 后的调用链：

```
NextNumberController::__invoke()
    │
    ├─ $serial->setModel($payment)
    ├─ $serial->setModelObject($request->model_id)
    │       │
    │       └─ Payment::find($model_id)
    │           │
    │           ├─ 如果找到 → 保留 sequence_number
    │           └─ 如果找不到 → nextSequenceNumber 保持 null
    │
    └─ $serial->getNextNumber()
```

### 5.3 问题：`route.params.id` 在不同路由下的语义混淆

这是核心问题所在。`selectNewCustomer` 中的 `if (route.params.id)` 条件不区分路由名：

| 路由名 | `route.params.id` | `model_id` 传入后端 | `Payment::find()` 查找 | 结果 |
|--------|-------------------|--------------------|-----------------------|------|
| `payments.create` | `undefined` | 不传入 | — | 正确：新建模式不保留序号 |
| `invoice.payments.create` | **发票 ID (如 42)** | **传入发票 ID** | `Payment::find(42)` → **null** | ⚠️ 语义错误：查的是 Payment 表但传入的是 Invoice ID |
| `payments.edit` | **付款 ID (如 7)** | 传入付款 ID | `Payment::find(7)` → **找到** | 正确：编辑模式保留序号 |

### 5.4 从发票跳转时的实际行为

当从发票详情页跳转后，用户切换客户时：

```
1. selectNewCustomer(新客户ID) 被调用
2. params.model_id = route.params.id = 42（发票 ID）
3. 后端 NextNumberController 收到 model_id = 42
4. $serial->setModelObject(42)
5. Payment::find(42) → 返回 null（42 是发票 ID，不是付款 ID）
6. $this->ob = null
7. if ($this->ob && $this->ob->sequence_number) → 条件不满足
8. nextSequenceNumber 保持 null
9. setNextNumbers() 中：null ? null : setNextSequenceNumber()
10. 重新计算 MAX+1 → 结果正确（虽然绕了个弯）
```

**结论**：虽然传入了错误的 `model_id`（发票 ID 而非付款 ID），但由于 `Payment::find(42)` 返回 `null`，`setModelObject` 的保留逻辑被跳过，退化为重新计算。**最终结果恰好正确**，但这是一个「负负得正」的巧合。

### 5.5 潜在风险

如果恰好存在 ID 为 42 的 Payment 记录（与发票 ID 相同），则：

```
Payment::find(42) → 返回该付款记录（可能是其他客户的付款！）
    │
    ├─ nextSequenceNumber = 该付款的 sequence_number（错误保留）
    └─ nextCustomerSequenceNumber 可能也会被错误保留
```

这将导致新建付款的编号与已有付款编号冲突。

## 6. 后端 NextNumberController 对 model_id 的解析逻辑

### 6.1 完整控制器代码

**代码位置** [NextNumberController.php](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/Admin/General/NextNumberController.php)

```php
public function __invoke(Request $request, Invoice $invoice, Estimate $estimate, Payment $payment)
{
    $key = $request->key;
    $serial = (new SerialNumberFormatter)
        ->setCompany($request->header('company'))
        ->setCustomer($request->userId);

    switch ($key) {
        case 'invoice':
            $nextNumber = $serial->setModel($invoice)
                ->setModelObject($request->model_id)  // Invoice::find(model_id)
                ->getNextNumber();
            break;

        case 'estimate':
            $nextNumber = $serial->setModel($estimate)
                ->setModelObject($request->model_id)  // Estimate::find(model_id)
                ->getNextNumber();
            break;

        case 'payment':
            $nextNumber = $serial->setModel($payment)
                ->setModelObject($request->model_id)  // Payment::find(model_id)
                ->getNextNumber();
            break;
    }

    return response()->json([
        'nextNumber' => $nextNumber,
    ]);
}
```

### 6.2 `model_id` 的解析流程

```
HTTP 请求: GET /api/v1/next-number?key=payment&userId=2&model_id=42
    │
    ▼
$request->model_id = "42"（字符串，自动转为 int）
    │
    ▼
$serial->setModel($payment)  // $this->model = Payment::class
    │
    ▼
$serial->setModelObject(42)
    │
    ├─ $this->ob = Payment::find(42)
    │
    ├─ if ($this->ob && $this->ob->sequence_number)
    │   └─ $this->nextSequenceNumber = $this->ob->sequence_number  // 保留
    │
    └─ if (isset($this->ob) && $this->ob->customer_sequence_number
           && isset($this->customer) && $this->ob->customer_id == $this->customer->id)
       └─ $this->nextCustomerSequenceNumber = $this->ob->customer_sequence_number  // 保留
```

### 6.3 `setModelObject` 的行为分类

| `model_id` 值 | `Payment::find()` 结果 | 行为 |
|--------------|----------------------|------|
| `null` | — | 不调用，`nextSequenceNumber` 保持 null → 重新计算 |
| 不存在的 ID | `null` | `$this->ob = null` → 保留条件不满足 → 重新计算 |
| **其他付款记录的 ID** | 返回错误记录 | ⚠️ **错误保留**：使用了错误记录的序号 |
| 正确的付款 ID（编辑模式） | 返回当前记录 | ✅ 正确保留 |

### 6.4 后端没有对 `model_id` 做任何校验

后端直接将 `model_id` 传入 `Model::find()`，没有任何校验：
- 不验证 `model_id` 是否属于当前公司（`company_id`）
- 不验证 `model_id` 是否属于当前用户有权限操作的对象
- 不验证 `model_id` 的类型是否匹配（如传入发票 ID 到 Payment 查询）

## 8. 发现的问题与改进建议

### 8.1 Bug：`route.params.id` 语义混淆导致 `model_id` 传入错误值

**严重程度**：中（当前因"负负得正"未造成实际错误，但存在 ID 碰撞风险）

**问题描述**：[Create.vue:L524](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/resources/scripts/admin/views/payments/Create.vue#L524-L524) 中 `if (route.params.id) params.model_id = route.params.id` 不区分路由名，将从发票跳转时的发票 ID 作为 `model_id` 传入后端。

**建议修复**：

```javascript
function selectNewCustomer(id) {
  let params = { userId: id }

  // 仅在编辑模式下传入 model_id（此时 route.params.id 是付款 ID）
  if (isEdit.value && route.params.id) {
    params.model_id = route.params.id
  }

  paymentStore.currentPayment.invoice_id = null
  selectedInvoice.value = null
  paymentStore.currentPayment.amount = 0
  invoiceList.value = []
  paymentStore.getNextNumber(params, true)
}
```

### 8.2 后端 `model_id` 缺乏校验

**问题描述**：[NextNumberController.php](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/Admin/General/NextNumberController.php) 直接将 `model_id` 传入 `Model::find()`，不验证归属和类型。

**建议改进**：
1. 在 `setModelObject` 中增加 `company_id` 校验
2. 在 `NextNumberController` 中增加 `model_id` 类型校验

```php
public function setModelObject($id = null)
{
    $this->ob = $this->model::where('id', $id)
        ->where('company_id', $this->company)  // 确保属于当前公司
        ->first();

    // ... 其余逻辑不变
}
```

### 8.3 路由设计建议

当前 `payments/:id/create` 和 `payments/:id/edit` 共用同一个 `:id` 参数但含义不同，建议改为语义更清晰的设计：

```javascript
// 当前（有歧义）
{ path: 'payments/:id/create', name: 'invoice.payments.create' }  // :id = 发票ID
{ path: 'payments/:id/edit', name: 'payments.edit' }               // :id = 付款ID

// 建议（消除歧义）
{ path: 'payments/create/from-invoice/:invoiceId', name: 'invoice.payments.create' }
{ path: 'payments/:paymentId/edit', name: 'payments.edit' }
```

## 9. 总结

### 9.1 `route.params.id` 的语义矩阵

| 路由 | `:id` 含义 | 在 `setInvoiceFromUrl` 中 | 在 `selectNewCustomer` 中 |
|------|-----------|--------------------------|-------------------------|
| `payments.create` | 不存在 | 不执行 | 不传入 `model_id` ✅ |
| `invoice.payments.create` | **发票 ID** | 正确使用（`fetchInvoice`） | ⚠️ 错误传入 `Payment::find()` |
| `payments.edit` | **付款 ID** | 不执行（`isEdit=true`） | 正确传入 `Payment::find()` ✅ |

### 9.2 客户切换后 `model_id` 出现在取号请求中的原因

`selectNewCustomer` 函数中 `if (route.params.id) params.model_id = route.params.id` 的条件**只检查 `route.params.id` 是否存在，不检查路由名**。当从发票详情页跳转时，`route.params.id` 是发票 ID（存在），因此被错误地作为 `model_id` 传入。

### 9.3 后端解析 `model_id` 的逻辑

后端通过 `setModelObject($request->model_id)` → `$this->model::find($id)` 查询对应模型的记录。如果找到记录，则保留其 `sequence_number`；如果找不到（返回 null），则退化为重新计算。

当前从发票跳转的场景中，`Payment::find(发票ID)` 返回 null，退化为重新计算，结果恰好正确。但如果存在 ID 碰撞（Payment 表中恰好有与发票 ID 相同的记录），将导致编号错误。
