#### 2.2.3 后端保存：Invoice::createInvoice

**创建方法** [Invoice.php:L326-L345](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Models/Invoice.php#L326-L345)：

```php
public static function createInvoice($request)
{
    $data = $request->getInvoicePayload();  // invoice_number 在这里面，来自前端

    $invoice = Invoice::create($data);       // 第一步：直接保存前端传来的 invoice_number

    // 第二步：后端独立重新计算序列号（不依赖前端）
    $serial = (new SerialNumberFormatter)
        ->setModel($invoice)
        ->setCompany($invoice->company_id)
        ->setCustomer($invoice->customer_id)
        ->setNextNumbers();

    // 第三步：将后端独立计算的序号保存到 sequence_number 字段
    $invoice->sequence_number = $serial->nextSequenceNumber;
    $invoice->customer_sequence_number = $serial->nextCustomerSequenceNumber;

    // 第四步：生成 Hashids 混淆标识
    $invoice->unique_hash = Hashids::connection(Invoice::class)->encode($invoice->id);
    $invoice->save();

    return $invoice;
}
```

### 2.3 双轨模式的设计意图

| 字段 | 来源 | 用途 |
|------|------|------|
| `invoice_number` | 前端调用 API 预览后提交（用户可修改） | 打印在 PDF 上，展示给客户 |
| `sequence_number` | 后端独立计算的纯数字递增序号 | 内部排序、编号溯源 |
| `customer_sequence_number` | 后端独立计算（按客户维度） | 客户维度的编号统计 |
| `unique_hash` | 后端基于自增 ID 生成的 Hashids | 公开 URL 中的标识符 |

**重要**：`invoice_number` 和 `sequence_number` 理论上应该保持一致（因为前端预览和后端计算使用相同逻辑），但用户可以手动修改 `invoice_number`，此时两者会出现差异。后端以 `sequence_number` 作为权威递增计数器。

## 3. 编辑现有单据：序号保留与重算逻辑

### 3.1 核心方法：setModelObject()

这是理解编辑行为的关键，定义于 [SerialNumberFormatter.php:L43-L56](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L43-L56)：

```php
public function setModelObject($id = null)
{
    $this->ob = $this->model::find($id);

    // 如果已有 sequence_number，则直接使用（保留）
    if ($this->ob && $this->ob->sequence_number) {
        $this->nextSequenceNumber = $this->ob->sequence_number;
    }

    // 如果已有 customer_sequence_number 且客户未变化，则直接使用（保留）
    if (isset($this->ob) 
        && isset($this->ob->customer_sequence_number) 
        && isset($this->customer) 
        && $this->ob->customer_id == $this->customer->id) {
        $this->nextCustomerSequenceNumber = $this->ob->customer_sequence_number;
    }

    return $this;
}
```

### 3.2 保留 vs 重算 判定表

#### 3.2.1 `sequence_number`（公司全局递增序号）

| 场景 | 行为 | 代码位置 |
|------|------|---------|
| 已有 `sequence_number` 值 | **保留原值** | [SerialNumberFormatter.php:L47-L49](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L47-L49) |
| 该值为空或 null | **重新计算**（MAX+1） | [SerialNumberFormatter.php:L106-L107](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L106-L107) |

#### 3.2.2 `customer_sequence_number`（客户维度递增序号）

| 场景 | 行为 | 代码位置 |
|------|------|---------|
| 已有值 **且** 客户 ID 未变化 | **保留原值** | [SerialNumberFormatter.php:L51-L53](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L51-L53) |
| 已有值 **但** 客户 ID 已变化 | **重新计算**（新客户的 MAX+1） | 条件不满足，fallback 到 `setNextCustomerSequenceNumber()` |
| 值为空或 null | **重新计算** | fallback 逻辑 |

#### 3.2.3 `invoice_number`（表单编号）

| 场景 | 行为 |
|------|------|
| 编辑时前端保留原值 | 用户可手动修改，后端直接接收 |
| 数据库唯一约束 | 同一 `company_id` 下必须唯一（忽略自身）|

### 3.3 编辑时的完整调用链

**Invoice::updateInvoice()** [Invoice.php:L375-L451](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Models/Invoice.php#L375-L451)：

```php
public function updateInvoice($request)
{
    $serial = (new SerialNumberFormatter)
        ->setModel($this)
        ->setCompany($this->company_id)
        ->setCustomer($request->customer_id)
        ->setModelObject($this->id)    // ← 关键：传入现有单据 ID，触发保留逻辑
        ->setNextNumbers();            // ← 内部会先检查是否已被 setModelObject 赋值

    $data = $request->getInvoicePayload();

    // 业务规则校验
    if ($total_paid_amount > 0 && $this->customer_id !== $request->customer_id) {
        return 'customer_cannot_be_changed_after_payment_is_added';
    }

    // 只有 customer_sequence_number 会被更新
    // sequence_number 和 invoice_number 都不在 $data 中被覆盖
    $data['customer_sequence_number'] = $serial->nextCustomerSequenceNumber;

    $this->update($data);
    // ...
}
```

**注意**：在 `updateInvoice()` 中，只有 `customer_sequence_number` 被显式写入更新数据。`sequence_number` 和 `invoice_number` 都不会被后端自动修改——除非用户在前端表单中手动修改了 `invoice_number`。

### 3.4 客户变化时的特殊行为

当编辑时更换了客户，触发以下连锁反应：

```
客户 ID 从 A 变为 B
        │
        ▼
setModelObject() 中条件不满足：
$this->ob->customer_id (A) != $this->customer->id (B)
        │
        ▼
fallback 到 setNextCustomerSequenceNumber()
        │
        ▼
查询"公司 X + 客户 B"的最大 customer_sequence_number
        │
        ▼
MAX + 1（或从 1 开始）作为新的 customer_sequence_number
```

同时还有业务层拦截：**如果该发票已有付款记录，则禁止更换客户** [Invoice.php:L389-L391](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Models/Invoice.php#L389-L391)：

```php
if ($total_paid_amount > 0 && $this->customer_id !== $request->customer_id) {
    return 'customer_cannot_be_changed_after_payment_is_added';
}
```

## 4. 重复生成编号：引用号与随机段的变化分析

### 4.1 引用号（reference_number）的行为分析

#### 4.1.1 Clone（克隆）场景

**CloneInvoiceController** [CloneInvoiceController.php:L61-L67](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/Admin/Invoice/CloneInvoiceController.php#L61-L67)：

```php
$newInvoice = Invoice::create([
    // ...
    'invoice_number' => $serial->getNextNumber(),          // ← 重新生成：新编号
    'sequence_number' => $serial->nextSequenceNumber,      // ← 重新计算：新序号
    'customer_sequence_number' => $serial->nextCustomerSequenceNumber, // ← 重新计算
    'reference_number' => $invoice->reference_number,     // ← 直接复制原单据的引用号
    // ...
]);
```

**结论（克隆场景）**：
- ✅ `invoice_number`：**变化** — 生成全新编号
- ✅ `reference_number`：**不变** — 原样复制原单据的引用号

#### 4.1.2 Convert（报价单转发票）场景

**ConvertEstimateController** [ConvertEstimateController.php:L56-L64](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/Admin/Estimate/ConvertEstimateController.php#L56-L64)：

```php
$invoice = Invoice::create([
    // ...
    'invoice_number' => $serial->getNextNumber(),          // ← 生成新的发票编号
    'sequence_number' => $serial->nextSequenceNumber,
    'customer_sequence_number' => $serial->nextCustomerSequenceNumber,
    'reference_number' => $serial->getNextNumber(),       // ← 这里有个 Bug！再次调用生成
    // ...
]);
```

**⚠️ 发现代码缺陷**：`reference_number` 居然也调用了 `$serial->getNextNumber()`。这意味着：
- 连续两次调用 `getNextNumber()`，由于没有中间落库，两次返回的是**同一个编号**
- 但如果 `setNextNumbers()` 内部状态发生变化，可能导致不一致

更合理的做法应该是复制报价单的 `estimate_number` 或 `reference_number`，而不是重新生成。

#### 4.1.3 RecurringInvoice（周期性发票）场景

**RecurringInvoice::createInvoice()** [RecurringInvoice.php:L308-L356](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Models/RecurringInvoice.php#L308-L356)：

```php

$newInvoice['sequence_number'] = $serial->nextSequenceNumber;
$newInvoice['customer_sequence_number'] = $serial->nextCustomerSequenceNumber;
// 注意：这里没有设置 reference_number！
```

**结论**：周期性发票生成时，`reference_number` 默认为 `null`。

### 4.2 随机段（RANDOM_SEQUENCE）的变化分析

#### 4.2.1 随机段的实现

[SerialNumberFormatter.php:L206-L210](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L206-L210)：

```php
case 'RANDOM_SEQUENCE':
    $value = $value ? $value : 6;
    $serialNumber .= substr(bin2hex(random_bytes($value)), 0, $value);
    break;
```

每次调用 `generateSerialNumber()`（即每次 `getNextNumber()`）都会执行 `random_bytes()`，因此：
- **每次调用都生成全新的随机字符串**
- 与递增序号不同，随机段**没有任何保留机制**

#### 4.2.2 各种场景下随机段的变化

| 场景 | 随机段是否变化 | 原因 |
|------|--------------|------|
| 新建单据（预览编号） | — | 首次生成 |
| 新建单据（正式保存） | **是** | 后端独立再调一次 `getNextNumber()` |
| 编辑单据（预览） | **是** | NextNumberController 重新调用 |
| 编辑单据（实际保存） | **视情况** | 如果用户未改 invoice_number 则不变；改了则后端不重算 |
| 克隆单据 | **是** | 新单据调用 `getNextNumber()` |
| 报价单转发票 | **是** | 两次调用 `getNextNumber()`，各生成一次 |
| 周期性发票 | **是** | 每个周期都重新生成 |

#### 4.2.3 关键风险：预览与保存的随机段不一致

在"前端预览 → 用户保存"的双轨模式下：
1. 前端调用 `/api/v1/next-number`，生成 `INV-a3f7b2-00042`（随机段为 `a3f7b2`）
2. 用户点击保存，将 `invoice_number=INV-a3f7b2-00042` 提交后端
3. 后端保存时，`invoice_number` **直接使用前端传来的值**
4. 但后端内部计算的 `sequence_number` 是独立的（与随机段无关）

因此，只要用户不手动修改表单中的 `invoice_number`，随机段就**不会变化**。真正的变化风险在用户手动编辑编号时。

### 5.2 Laravel 路由模型绑定的自定义键

语法 `{invoice:unique_hash}` 是 Laravel 的**自定义键路由模型绑定**（Custom Key Route Model Binding）。

工作原理：
```
HTTP 请求: GET /invoices/pdf/XKAR7m8jD2bqP9OSVeNG
                    │
                    ▼
        路由参数解析: invoice = XKAR7m8jD2bqP9OSVeNG
                    │
                    ▼
        Laravel 自动执行查询:
        SELECT * FROM invoices 
        WHERE unique_hash = 'XKAR7m8jD2bqP9OSVeNG'
        LIMIT 1
                    │
                    ▼
        将查询到的 Invoice 实例注入到控制器方法
```

### 5.3 控制器中的使用

**InvoicePdfController** [InvoicePdfController.php](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/PDF/InvoicePdfController.php)：

```php
public function __invoke(Request $request, Invoice $invoice)
{
    // $invoice 已经是通过 unique_hash 查询到的模型实例！
```

### 5.7 Hashids 解码（反向定位）

虽然公开路由直接通过 `unique_hash` 字段查询数据库，但 Hashids 本身支持解码还原为原始 ID。

示例：
```php
// 编码（创建时）
$unique_hash = Hashids::connection(Invoice::class)->encode($invoice->id);
// 例如 id=42 → "XKAR7m8jD2bqP9OSVeNG"

// 解码（需要时）
$decoded = Hashids::connection(Invoice::class)->decode($unique_hash);
// 返回 [42]，可直接获取原始 id
```

这为内部系统提供了"从公开 URL 反查原始记录"的能力，而无需查询数据库。

### 6.2 双轨模式下编号不一致的潜在问题

当前设计中，前端预览的 `invoice_number` 可能与后端实际计算的不一致：
1. 用户 A 打开新建页面，获取预览编号 `INV-000042`
2. 用户 B 在另一个窗口快速创建了一张发票，占用了 `INV-000042`
3. 用户 A 提交保存，由于唯一约束，可能会失败（尽管 FormRequest 有验证）

**建议**：考虑使用数据库事务 + 悲观锁，或者在保存时后端重新生成编号（如果用户未手动修改）。

### 6.3 随机段的唯一性未校验

`RANDOM_SEQUENCE` 使用 `random_bytes()` 生成，虽然碰撞概率极低，但没有唯一性校验。

**建议**：生成后在同 `company_id` 范围内检查是否已存在。

## 7. 总结

### 7.1 新建保存流程

编号采用 **"前端预览 + 后端独立计算"** 的双轨模式：
- 前端：通过 `/api/v1/next-number` 预览编号，填入表单
- 后端：接收前端传入的 `invoice_number` 直接入库，同时独立计算 `sequence_number` 作为权威序号

### 7.2 编辑时的序号保留规则

| 字段 | 保留条件 | 重算条件 |
|------|---------|---------|
| `sequence_number` | 已有值时始终保留 | 仅当值为 null 时 |
| `customer_sequence_number` | 已有值 **且** 客户 ID 未变化 | 客户变化 **或** 值为 null |
| `invoice_number` | 用户未手动修改时不变 | 用户修改后随表单提交 |
| `unique_hash` | **永不变化**（绑定自增 ID） | — |

### 7.3 引用号与随机段的变化

| 场景 | `reference_number` | 随机段 `RANDOM_SEQUENCE` |
|------|-------------------|------------------------|
| 克隆 | **复制原值** | **重新生成** |
| 报价单转发票 | Bug（重新生成）| **重新生成（两次）** |
| 周期性发票 | 留空 | **重新生成** |
| 编辑（不换客户） | 不变 | 不变（随 `invoice_number` 保留） |
| 编辑（换客户） | 不变 | 不变（同上） |

### 7.4 混淆标识的定位机制

- **路由层**：使用 Laravel 自定义键路由模型绑定 `{invoice:unique_hash}`
- **ORM 层**：自动执行 `WHERE unique_hash = ?` 查询并注入模型实例
- **安全层**：`PdfMiddleware` 检查三种 Guard（web/sanctum/customer）任一通过即可
- **备用机制**：Hashids 可解码还原为原始 `id`，无需查询数据库即可定位
