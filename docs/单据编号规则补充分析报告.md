### 2.1 三个单据 Store 的 `getNextNumber` 方法签名对比

| **报价单** | `getNextNumber(params, setState = false)` | `this.newEstimate.estimate_number` |
| **付款单** | `getNextNumber(params, setState = false)` | `this.currentPayment.payment_number` |

以发票为例的实现 [invoice.js:L360-L375](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/resources/scripts/admin/stores/invoice.js#L360-L375)：

```javascript
getNextNumber(params, setState = false) {
  return new Promise((resolve, reject) => {
    http
      .get(`/api/v1/next-number?key=invoice`, { params })
```

### 2.3 三者对比总结

| 维度 | 发票 | 报价单 | 付款单 |
|------|------|-------|-------|
| **写回方式** | `.then()` 中手动赋值 | 同左 | 同左 |
| **新建模式** | ✅ 写回 | ✅ 写回 | ✅ 写回（同时初始化日期、币种） |
| **编辑模式** | ❌ 不写回（用数据库值） | ❌ 不写回 | ❌ 不写回 |
| **调用 `getNextNumber` 时 setState** | `false` | `false` | `false` |
| **编辑时初始化的额外内容** | 加载发票数据 | 加载报价单数据 + 销售税 | 加载付款数据 + 计算 maxPayableAmount |

**设计意图**：统一使用 `Promise.all` 并行请求多个初始化数据，然后在 `.then()` 中统一写入状态，避免多次触发响应式更新。

## 4. 重复格式化：随机段与引用号的变化规律

### 4.1 递增序号的缓存机制

SerialNumberFormatter 内部对两个递增序号有 **"已赋值则跳过"** 的缓存逻辑：

**代码位置**：[SerialNumberFormatter.php:L104-L113](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L104-L113)

```php
public function setNextNumbers()
{
    $this->nextSequenceNumber ?
        $this->nextSequenceNumber : $this->setNextSequenceNumber();

    $this->nextCustomerSequenceNumber ?
        $this->nextCustomerSequenceNumber : $this->setNextCustomerSequenceNumber();

    return $this;
}
```

这是三元运算符的简写，等价于：

```php
if (! $this->nextSequenceNumber) {
    $this->setNextSequenceNumber();
}
if (! $this->nextCustomerSequenceNumber) {
    $this->setNextCustomerSequenceNumber();
}
```

### 4.2 多次调用 `getNextNumber()` 的完整状态变化

假设格式为 `{{SERIES:INV}}{{RANDOM_SEQUENCE:4}}{{SEQUENCE:4}}`，连续调用两次：

```php
$serial = (new SerialNumberFormatter)
    ->setModel(new Invoice)
    ->setCompany($companyId)
    ->setCustomer($customerId);

// 第一次调用
$result1 = $serial->getNextNumber();   // "INV-a3f7-0042"

// 第二次调用（同一实例）
$result2 = $serial->getNextNumber();   // "INV-b8d2-0042"
```

**两次调用的内部状态变化**：

| 内部属性 | 第 1 次调用前 | 第 1 次调用后 | 第 2 次调用后 |
|---------|-------------|-------------|-------------|
| `nextSequenceNumber` | `null` | `42`（查库 MAX+1） | `42`（**保持不变**） |
| `nextCustomerSequenceNumber` | `null` | `15`（查库 MAX+1） | `15`（**保持不变**） |
| 随机段结果 | — | `a3f7` | `b8d2`（**重新生成**） |

### 4.3 随机段的不可缓存性

**代码位置**：[SerialNumberFormatter.php:L206-L210](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Services/SerialNumberFormatter.php#L206-L210)

```php
case 'RANDOM_SEQUENCE':
    $value = $value ? $value : 6;
    $serialNumber .= substr(bin2hex(random_bytes($value)), 0, $value);
    break;
```

`random_bytes()` 在每次 `generateSerialNumber()` 调用时都会重新执行，**没有任何缓存或幂等保证**。

### 4.4 引用号（reference_number）的独立地位

**引用号完全不参与 SerialNumberFormatter 的格式化流程**，它属于业务层字段：

| 场景 | reference_number 来源 |
|------|---------------------|
| 新建发票 | 默认为 `null`（用户可手动填写） |
| 克隆发票 | 复制原发票的 `reference_number` |
| 报价单转发票 | ⚠️ Bug：错误地再次调用 `getNextNumber()` |
| 编辑发票 | 随表单直接更新，不自动变化 |

### 4.5 不同占位符组合下的重复格式化表现

| 格式示例 | 第 1 次结果 | 第 2 次结果 | 变化部分 |
|---------|-----------|-----------|---------|
| `{{SEQUENCE:6}}` | `000042` | `000042` | 无 |
| `{{CUSTOMER_SEQUENCE:4}}` | `0015` | `0015` | 无 |
| `{{RANDOM_SEQUENCE:6}}` | `a3f7b2` | `c9d4e1` | 全部变化 |
| `{{DATE_FORMAT:Y}}{{SEQUENCE}}` | `2024000042` | `2024000042` | 无（同日） |
| `{{RANDOM_SEQUENCE:4}}-{{SEQUENCE:4}}` | `a3f7-0042` | `b8d2-0042` | 仅随机段变化 |
| `{{SERIES}}{{DELIMITER}}{{SEQUENCE}}` | `INV-000042` | `INV-000042` | 无 |

**结论**：
- 只要格式中包含 `RANDOM_SEQUENCE`，同一实例多次调用的结果就会不同
- 只包含 `SEQUENCE` / `CUSTOMER_SEQUENCE` / `SERIES` / `DATE_FORMAT` 等确定性占位符时，结果保持一致
- 这就是前端设置页面的"预览"功能每次展示略有差异的根本原因

## 5. 对外公开链接：混淆标识的实际定位链路

系统中存在 **两套完全不同的公开路由机制**，定位方式也不同。

### 5.1 路由全景图

```
公开路由体系
├── 路由组 A：/invoices/pdf/{invoice:unique_hash}
│   ├── /estimates/pdf/{estimate:unique_hash}
│   ├── /payments/pdf/{payment:unique_hash}
│   └── 认证要求：pdf-auth（三选一：web/sanctum/customer）
│
└── 路由组 B：/customer/invoices/{email_log:token}
    ├── /customer/estimates/{email_log:token}
    ├── /customer/payments/{email_log:token}
    └── 认证要求：无（公开访问，通过 token 鉴权）
```

### 5.2 路由组 A：unique_hash + 路由模型绑定（需登录）

#### 5.2.1 定位原理

Laravel 的自定义键路由模型绑定（Custom Key Route Model Binding），**直接查库，不解码 Hashids**。

以发票为例：
```
GET /invoices/pdf/XKAR7m8jD2bqP9OSVeNG
            │
            ▼
Laravel 解析路由参数：invoice = "XKAR7m8jD2bqP9OSVeNG"
            │
            ▼
ORM 执行：SELECT * FROM invoices WHERE unique_hash = "XKAR7m8jD2bqP9OSVeNG" LIMIT 1
            │
            ▼
将 Invoice 实例注入控制器方法参数
```

#### 5.2.2 控制器实现

**代码位置**：[InvoicePdfController.php](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Http/Controllers/V1/PDF/InvoicePdfController.php)

### 5.4 Hashids 解码的实际使用情况

**整个项目中，Hashids::decode() 没有任何实际业务调用**。

搜索结果确认：
- `app/` 目录下 **不存在** 任何 `Hashids::decode()` 或 `HashidsManager::decode()` 调用
- 所有通过 `unique_hash` 定位记录的场景，全部使用 `Model::where('unique_hash', $hash)->first()` 直接查库
- 唯一出现 decode 字样的是前一份分析报告（纯演示代码）和 `json_decode()`（与 Hashids 无关）

**为什么没用解码？**

| 方案 | 实现方式 | 实际采用 |
|------|---------|---------|
| 方案 A：解码还原 ID 再查库 | `Hashids::decode($hash) → [42] → Invoice::find(42)` | ❌ 未采用 |
| 方案 B：直接按 unique_hash 查库 | `Invoice::where('unique_hash', $hash)->first()` | ✅ 实际采用 |

选择方案 B 的可能原因：
1. **实现简单**：Laravel 路由模型绑定原生支持自定义键，不需要额外中间层
2. **可读性好**：`WHERE unique_hash = ?` 比先解码再查询更直观
3. **性能不差**：`unique_hash` 字段上通常有唯一索引，查询效率高
4. **编码安全性**：避免暴露"Hashids 可还原为内部 ID"这一事实

## 6. 发现的问题汇总

### 6.1 ConvertEstimateController 的 reference_number Bug（已在报告 2 中指出）

仍然存在且未修复，具体见上一份报告。

### 6.2 付款单切换客户时不取号的潜在问题

付款单在 `onCustomerChange()` 中只取发票列表，不刷新付款编号。如果格式中使用了 `CUSTOMER_SEQUENCE`，则编号不会反映新客户的序号——尽管此时发票列表已更新为新客户的发票。这是一个**行为不一致**，虽然可能是有意设计，但缺乏文档说明。

### 6.3 随机段在预览时的不稳定表现

设置页面中，用户编辑格式字符串时，每次预览如果包含 `RANDOM_SEQUENCE`，展示结果都会变化。这可能让用户误以为格式设置有问题，实际是正常行为。建议预览时用固定的随机种子，保证同一格式的预览结果稳定。

### 6.4 EmailLog::isExpired() 的性能问题

[EmailLog.php:L23](file:///d:/fz/0601-1/solo-dogfeeding/code/22-InvoiceShelf/app/Models/EmailLog.php#L23-L23)：

```php
$linkExpiryDays = (int) CompanySetting::getSetting('link_expiry_days', $this->mailable()->get()->toArray()[0]['company_id']);
```

每次判断过期都会执行完整查询：
1. `$this->mailable()->get()` — 执行关联查询
2. `toArray()` — 转换整个结果集
3. 取 `[0]['company_id']` — 手动取第一条的字段
4. 再查一次 `CompanySetting`

建议优化为 `$this->mailable->company_id`（Eager Loading）或直接在 EmailLog 上冗余存储 `company_id`。

## 7. 总结

### 7.1 初始化写回时机

三个单据均采用 **"并行请求 → Promise.all 汇总 → .then() 中仅在新建模式下写回"** 的模式，编辑模式由 API 加载原值覆盖。

### 7.2 切换客户的取号行为

| 单据 | 客户切换 | 发票切换 |
|------|---------|---------|
| 发票 | ✅ BaseCustomerSelectPopup 触发 `getNextNumber(params, true)` | N/A |
| 报价单 | ✅ 同左 | N/A |
| 付款单 | ❌ 仅拉发票列表，不取号 | ✅ `onSelectInvoice()` 中触发取号 |

### 7.3 重复格式化的变化规律

SerialNumberFormatter 内部通过 `setNextNumbers()` 中的三元判断缓存了两个递增序号，但 `RANDOM_SEQUENCE` 每次调用 `generateSerialNumber()` 都会重新生成。因此：
- **纯确定性占位符**（SEQUENCE / SERIES / DATE_FORMAT 等）：多次格式化结果一致
- **含 RANDOM_SEQUENCE**：每次结果的随机段都不同
- **reference_number**：完全独立于该服务，属业务层字段

### 7.4 混淆标识的定位机制

| 路由类型 | 定位方式 | 是否解码 Hashids |
|---------|---------|----------------|
| `/invoices/pdf/{invoice:unique_hash}` | Laravel 路由模型绑定，`WHERE unique_hash = ?` 直接查库 | ❌ 不解码 |
| `/customer/invoices/{email_log:token}` | 先按 token 查 EmailLog，再用多态 mailable_id 反查单据 | ❌ 不涉及 |
| 报表 API | `Company::where('unique_hash', $hash)->first()` | ❌ 不解码 |

**Hashids 的 decode 能力在项目中完全未被使用**，所有定位都通过数据库查询完成。Hashids 仅作为"编码工具"单向使用，从未逆向解码。
